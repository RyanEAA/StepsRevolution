# Host Asset Relay Architecture

## Decision

Only the room host imports StepMania files. Guests receive temporary preview
assets, the confirmed song audio, and normalized gameplay charts through an
authenticated HTTPS relay owned by the existing room server.

Socket.IO remains responsible for small canonical state and commands. It does
not carry full audio files. The relay streams binary uploads and downloads so
large buffers do not block room snapshots, readiness, scores, or clock traffic.

The current local-library matching flow remains operational while this design
is implemented incrementally. It will be removed only after the relay,
verification, per-player chart selection, and browser preparation flow pass
two-client testing.

## Canonical ownership

The host is the source of song content. The server is the temporary transport
and canonical room authority.

The server owns:

- preview and song-package revisions
- temporary asset identifiers and expiry
- upload/download authorization
- accepted song-package metadata
- the available chart descriptors
- each player's chart choice and preparation status
- readiness eligibility

The host owns locally:

- imported `File` objects and object URLs
- preview generation
- source audio bytes
- source simfile parsing
- canonical runtime-chart package generation

Guests own locally:

- downloaded blobs
- SHA-256 verification results
- decoded audio buffers
- their selected chart
- local preparation errors

No room snapshot contains a `File`, object URL, raw audio buffer, or reconnect
credential.

## Two asset moments

### Song browsing preview

When the host opens a song modal:

1. The host publishes song display metadata.
2. Artwork is uploaded if it is not already cached for the room.
3. The browser generates a short preview from decoded audio.
4. The preview is encoded as a small mono/downsampled WAV asset.
5. The server validates, stores, and hashes the assets.
6. A canonical preview snapshot references their opaque asset IDs.
7. Guests download and play the preview.

Closing the modal publishes `preview.clear`. Rapid browsing increments
`previewRevision`; clients ignore older downloads that complete afterward.

The initial limits are:

| Asset | Maximum |
| --- | ---: |
| Artwork | 5 MiB |
| Preview audio | 2 MiB |
| Full song audio | 100 MiB |
| Runtime chart package | 5 MiB |

### Confirmed song package

When the host confirms a song:

1. The host uploads the original audio file once.
2. The host serializes every supported difficulty into one normalized runtime
   chart package.
3. The server verifies both upload hashes before accepting the package.
4. The canonical room selection becomes one song with many chart descriptors.
5. Each guest downloads audio and chart data from the relay.
6. Each guest verifies SHA-256 before decoding or becoming prepared.
7. Every player selects one chart from the accepted descriptor list.
8. Ready is allowed only after that player's audio is verified and decoded and
   their chosen chart belongs to the current package revision.

## Runtime chart package

The chart package contains only gameplay-relevant normalized data:

```text
asset protocol version
song identity
song offset
normalized BPM segments
charts[]
  chart identity
  runtime-compatible chart hash
  normalized notes
    lane
    beat
    hit time
```

It deliberately excludes source comments, source filenames, artwork paths,
unsupported StepMania tags, and browser-local references.

## Planned relay endpoints

Asset authorization is negotiated through the authenticated Socket.IO room
session. Reconnect tokens are never placed in URLs.

```text
asset.upload.request
  -> host-only, one-time upload ticket

PUT /relay/assets/:assetId
  Authorization: Bearer <one-time-upload-ticket>
  Content-Length required
  Content-Type allowlisted per asset kind
  server streams to a temporary file while hashing

asset.download.request
  -> room-member, short-lived download ticket

GET /relay/assets/:assetId
  Authorization: Bearer <short-lived-download-ticket>
  supports streaming and Range requests
```

The server commits an upload only after byte length, MIME type, SHA-256, room,
uploader, asset kind, and expiry all match the reservation. Failed partial
uploads are deleted.

## Storage lifecycle

The MVP uses a configured temporary directory, not process memory.

- one directory per room
- random opaque filenames generated by the server
- no user-provided path components
- atomic temporary-file rename after verification
- deletion when a preview is superseded when practical
- deletion when a song package is replaced
- deletion when a room closes or expires
- startup sweep for abandoned expired directories
- per-room and per-player quotas

Production deployment must account for disk capacity, upload timeouts, and
reverse-proxy body/streaming settings.

## Migration sequence

### R1 — Shared relay contract

- strict asset descriptors and byte limits
- preview and song-package schemas
- normalized runtime chart-package schema
- per-player chart choice and preparation schema
- proposed Socket.IO command schemas
- no runtime behavior replacement

### R2 — Temporary asset relay server

- [x] secure temporary directory
- [x] host-only upload and room-member download tickets
- [x] streaming PUT/GET endpoints with byte-range downloads
- [x] incremental SHA-256 verification
- [x] MIME and declared-length verification
- [x] per-room quotas, asset expiry, and room-close cleanup
- [x] CORS support for configured browser origins
- [x] HTTP, Socket.IO, authorization, hash, range, quota, and lifecycle tests

R2 intentionally has no visible preview UI. It supplies the authenticated
transport used by R3 and R4.

### R3 — Shared modal previews

- [x] host-side 22.05 kHz mono PCM preview generation
- [x] artwork and preview upload with SHA-256 verification
- [x] server-authoritative, host-only preview revisions
- [x] guest-only preview display and verified download
- [x] autoplay with a manual playback fallback
- [x] stale generation/download cancellation and object-URL cleanup

R3 keeps the Stage 8 local-library chart matching flow as a compatibility
fallback. Full song audio and chart packages are deliberately deferred to R4;
per-player difficulty choice and the removal of guest library imports belong
to R5.

### R4 — Confirmed song transfer

- [x] song preview and difficulty selection split into separate steps
- [x] host confirmation uploads the original audio asset
- [x] normalized runtime package includes every indexed dance-single chart
- [x] server validates that committed audio/chart/artwork assets are room-owned and ready
- [x] every client downloads and SHA-256 verifies the canonical assets
- [x] preparation and failure state is stored per player
- [x] difficulty buttons unlock only after local package preparation
- [x] each player publishes an independent chart choice
- [x] guests no longer import a local song library

The prepared audio blob and normalized runtime charts remain in browser memory.
R5 will connect each player’s selected runtime chart to prepared gameplay and
finish the ready/start policy.

### R5 — Per-player difficulty and readiness

- [x] chart options rendered for every player
- [x] one server-validated chart choice per player
- [x] readiness requires verified prepared audio and a valid chart
- [x] remove the transitional guest-library matching requirement
- [x] load each chosen runtime chart and prepared audio into gameplay
- [x] preserve prepared assets across ready-check and countdown transitions
- [x] rehydrate browser-local assets after refresh/reconnect
- [x] add explicit retry controls for failed transfers

Changing difficulty temporarily returns that player to `verifying`; readiness
is restored only after the selected normalized chart and decoded audio have
been loaded into the local game runtime. The online Start/Pause/Restart buttons
remain disabled until the synchronized countdown stage owns playback.

### R6 — Clock synchronization

- [x] five-sample client/server clock exchange
- [x] lowest-round-trip offset estimate and latency quality gate
- [x] periodic resampling while selecting or ready checking
- [x] Ready action unlocks Web Audio through a user gesture
- [x] host-only synchronized countdown after all players are ready
- [x] canonical server start timestamp five seconds ahead
- [x] translation into each client’s `performance.now()` clock
- [x] direct `AudioBufferSourceNode` scheduling on the Web Audio clock
- [x] countdown gameplay overlay and local game activation at the deadline
- [x] countdown cancellation when any client cannot schedule safely

After the start instant, `AudioClock` remains authoritative for chart time;
network clock estimates are not used to move notes or block the render loop.
Online Pause and Restart remain disabled.

### R7 — Live multiplayer game lifecycle

- [x] publish bounded live-score snapshots
- [x] render remote scores beside the playfield
- [x] report one final result per player for per-player package charts
- [x] wait for every active player or the result timeout
- [x] collect one replay vote per connected player
- [x] expose host replay confirmation after every replay vote
- [x] preserve prepared audio/chart choices for replay
- [x] host return-to-selection clears the package for every client
- [x] all clients return to the session after replay or song change
- [x] render multiplayer standings beside local results

The relayed-song result validator now resolves tap count and duration from each
player’s own chart choice rather than the removed shared-chart selection. Song
confirmation enters ready check immediately, so Ready is visible while assets
and difficulty are being prepared and becomes enabled as soon as both are
locally bound.

Live scores are observed outside the render loop at a maximum of ten updates
per second, with a one-second unchanged-score heartbeat. When the audio source
ends, the game now judges any remaining notes as misses and enters `finished`
instead of `paused`, guaranteeing that each client submits its final result.
Natural completion is checked against the authoritative Web Audio clock as
well as the source node's `ended` event, so a delayed browser event cannot
strand the room in `playing`.
Final-result commands are idempotent and retried until the sender observes its
result in a canonical room snapshot. This keeps replay, return-to-selection,
and the next song package from being blocked by a lost terminal update.
Accepted room commands also carry their canonical snapshot in the
acknowledgement, while broadcasts continue updating the other members. The
sender therefore cannot miss its own terminal state because of message order.
The server stores the final timestamp only in `finalResult`; the corresponding
`liveScore` snapshot contains score fields only, keeping completed room
snapshots valid under strict runtime schemas.

Room hosts can remove guests from the Session player list outside countdown
and gameplay. Removed players lose their reconnect token and receive an
explicit removal message. Each completed round awards a room-scoped win to the
highest final score (including tied winners); win stars persist through replay
and song changes until the room closes.

## Content and privacy boundary

The application must clearly tell hosts that selecting online transfer shares
the audio file with room members. Deployments should be used only for content
the participants are permitted to share. Room assets are temporary and are not
indexed, published, or retained as a permanent song library.
